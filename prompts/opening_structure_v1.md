# 三问开篇结构专项

你正在为北极星问题 3.1 和 3.2 建立一份共享的“前三章逐段任务与信息装载账本”。这不是剧情摘要，也不是给用户新书写开篇。

## 总原则

1. 只分析输入的前三章全部段落。程序会校验三章、段落顺序、连续覆盖、原文位置和来源版本。
2. 开场类型、段落功能、章节任务和信息模块归属属于文学判断，由你结合完整上下文判断。示例类型与六个信息模块都是观察框架，不是关键词表，也不是必须同时出现的硬门槛。
3. `paragraph_segments` 必须按章、按段落顺序覆盖每一段，不能跳段、重叠或倒序。相邻段落承担同一主要功能时合并成一个连续范围；功能变化时切段。
3.1 输入每章的 `paragraph_columns` 固定说明紧随其后的段落数组各列含义；数组第一列 `paragraph` 是你在所有返回位置中使用的段落号。
4. 书名、作者、简介、卷名、章节标题等正文外内容也要被范围覆盖，但标为 `FRONT_MATTER`；真正参与叙事的段落标为 `STORY`。不要因为输入分章方式不理想而静默丢段。
5. 每个 `STORY` 范围写一个具体主要功能，例如“用游戏失利展示主角处境”“用陌生来信打破日常”。不要为了整齐强行套固定类别。
6. `information_modules` 只标当前范围实际承载的模块，可以为空。六个模块分别是：主角困境、主角性格、核心能力、世界观规则、威胁、短期目标。一个范围可同时承载多个模块。
7. `module_assessments` 必须逐项返回六个模块；没有足够依据时使用 `NOT_OBSERVED`，不能为了通过结构校验硬说已经出现。`SUPPORTED` 的首次位置必须落在一个确实标有该模块的 `STORY` 范围内。
8. 3.1 只回答首章开场：开场类型、正文起点、主角首次出场段落、正在做什么、初始麻烦、第一句话与第一段的功能。类型可以使用“冲突进行时、悬念异象、日常被打破、穿越降临即打脸”等观察示例，也可以给出更贴合原文的其他类型。
9. 3.2 逐章说明第 1、2、3 章各自完成的任务，并给出关键事件段落；任务可以有多项，不要求每章都必须同时完成代入、困境、能力、爽点和留钩。
10. 只能使用输入原文。不得补写作者意图、读者留存、销量、口碑、跨书标准区间或用户新书方案。当前没有同品类多书对照时，把它写入 `limitations`。

## 输出

严格按输出结构返回一个 JSON 对象，不要输出 Markdown、前言或额外字段。段落号完全使用输入中的 `paragraph`，不要返回原文，不要自行计算字符位置；程序会把段落号转换为真实原文、累计字符和计数。
