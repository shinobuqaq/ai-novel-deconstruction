## 0. 接手项目时必须先执行的决策程序

本节高于文档后部的历史进度记录、旧“下一步”和实现便利。每次设计、规划下一步或判断完成度时，先执行本节；不能只搜索到一个功能名或一条旧进度就开始实施。

### 0.1 权威关系和决策优先级（上下文压缩后仍必须保留）

**永久记忆锚点**：用户拥有最高决策权，负责确定项目目标、大方向、使用方式、边界、预期效果、明确纠偏和最终验收；Fable 是本项目的总设计师，在不违背用户决定的前提下负责已经形成的具体策略和设计路线；Codex 和后续接手的 AI 是执行者，负责忠实落地、验证和同步，只有 Fable 确实没有设计完整的地方才可沿其思想补充。三者不是可以任意折中的平行意见来源。

1. **用户决定方向并拥有最终裁决权**：用户后来明确纠正的目标、边界和使用方式，覆盖 Fable 和其他 AI 的旧表述，也覆盖已经实现但建立在错误前提上的功能。用户通常可以用概括性指令、口语举例或示例数字说明想要的能力和效果；除非用户明确把某项实现细节定为新决定，不得把这些大方向或例子机械解释成对 Fable 既定详细设计的替代。例如 `50`、`200`、`1000` 表示章节数是任意合理变量，不表示产品只能支持三个固定档位。
2. **Fable 的已定详细路线必须继承**：在没有与用户当前决定发生真实冲突的部分，Fable 已核实的产品路线、问题框架、具体产出、证据标准、范围边界、补全方法和执行顺序，是后续设计与实现的默认约束。执行者不能因为个人偏好、实现方便、当前代码已经不同或认为另一方案更“先进”，就重新设计、优化掉或静默绕开。
3. **Codex 和后续 AI 只在真实留白处补充**：宣布“Fable 没说清”以前，必须先回查第 0.3 节原始对话、路线底稿和当前已迁移决定，区分已定决定、试探性建议、用户已否决内容、未决问题和后续补充。只有证据确认存在空白时，才能结合用户目标、Fable 已定原则和项目约束提出最小充分补充；补充必须标明“后续补充”或“后续推导”，不能伪称为 Fable 决定或用户已确认。
4. **文档、代码和测试都是载体或实现证据，不是更高权威**：本文件负责承载当前有效路线，代码和测试负责证明实现事实；它们已存在、接口能跑或自动测试通过，不得反过来改变前三项，也不等于内容质量、真实可用性或用户验收通过。发现载体与有效路线冲突时，应修正载体，而不是拿现状覆盖路线。

用户的新指令只覆盖与其真实冲突的部分，Fable 其余仍有效设计继续执行；不能把一次局部纠偏扩大成整条路线重置。若证据表明 Fable 的既定方案在现实条件下不可行，执行者必须先说明看到的证据、影响和需要用户裁决的冲突，不得静默换路线。

任何新会话、上下文压缩、上下文丢失或新 AI 接手后，必须先读本节、0.2 的有效决定和 0.3 的证据入口，再读当前实现和下一步。压缩摘要、上一个执行者的口头结论、现有代码、测试或旧进度都不能替代这项重新对齐。

发生冲突时必须写明“冲突的两项是什么、按哪一级裁决、清理了哪些文档/代码/测试/界面/计划”。没有原始对话、用户纠偏记录或当前基线依据时，不得使用“Fable 要求”“用户已确认”这类表述。

7. 新增或修改任何一问前，先把规则分成“客观事实校验”和“主观文学判断”两栏。只有前者可以成为程序硬失败；后者只能作为模型观察框架和用户可回查的解释，不得写成缺一不可的成立清单。42 问目录中的每一问都必须继承同一份版本化规则，自动测试必须保持 `42/42` 覆盖。

### 0.5 本次错误为什么会发生

- 后续 AI 把“七问报告对象、任务和页面能够运行”误判为“正式首批学习报告闭环”，混淆了工程通路和 Fable 要求的专项拆书原料。
- 当时的基线末尾保留了“下一步直接用在线模型跑七问”的错误计划，后续接手读取它后继续放大了偏差。
- Fable 优先级虽然后来被写入第 22 章进度记录，却没有成为文档开头的强制决策程序，正确原则无法约束前面的旧计划。
- “已有若干人物、剧情和深层分析结果”被错误等同于“足以回答北极星问题”，没有逐问检查具体实物、计数、证据和覆盖范围。
- 七问原型又使用“七问全部就绪才生成”的整体闸门，导致已经具备证据的题目也没有形成用户可判断的实际答案；`5/7` 被误读成进度，全量审计当时的真实状态其实是正式学习答案 `0/42`。
- 2.2 完成后，README、基线和页面标题一度仍保留“下一步 2.2”，诊断汇总也把早先取消任务与后来成功任务合成“等待开始”；这说明完成专项却不执行 0.4 第 6 条同步清理，同样会制造下一轮错误判断。本次已改为证据状态驱动并增加回归检查。
- 4.9 实现时把 3.4 的前三章兑现距离和 4.10 的悬念回收职责扩张到每个章末钩，33 章即生成 667 条回应候选；固定均衡抽 50 章又无法计算相邻章节的连续强钩与轮换，因此短实体书样本成功不能证明网文规模合同成立。
- 首组页面把人物专项账本、章末钩专项账本、五问答案和结算连续铺在同一滚动页，虽有卡片样式却没有把“用户答案、展开证据、内部账本”分层，重新制造了 Fable 已诊断的“找不到重点、不知道按什么顺序看”。
- 首组答案编译虽然做到逐问保存，却仍把五问和全部材料放进同一次模型请求；上下文预算只按“模型窗口装得下”放宽到 36 万字符，没有按问题相关性、任务复杂度和有效注意力设置软上限。
- 首组 2.1 提示词已经列出角色出场序、首场功能、后续戏份、新增间隔和功能分布，但通用返回结构只有结论、指标和证据，程序又只检查“有指标、有证据”；专项原料只给人数和零散开篇事件，没有可直接核对的首行动人物账本。因此模型只答 27/55/113 仍被保存。该遗漏首先证明“合同—原料—返回结构—程序验收”没有对齐，不能直接归因于 163,679 Token 长输入。
- 本机服务曾被一概视为适合整包返回；学习报告的完整 2.1 合同实际需要 15,892 输出 Token，gcli2api 非流式链路内部又按每轮 300 秒超时并最多重试 6 次。工作台连接先断、上游仍重试且结果不落盘，导致“模型可能生成、用户却拿不到”。同请求流式复测在 5.711 秒收到首个增量、187.374 秒完整结束，证明长输出任务不能继续沿用本机整包默认值。

以上不是一次措辞失误，而是判断入口和数据准入缺失造成的流程错误。本节与 0.4 的检查程序用于阻止同类问题再次发生。

## 2. 产品定义

### 2.1 产品目标

本项目的最终目标是让 AI 写作系统能够创作高质量的百万字中文网文。本项目当前交付的拆书器不是续写器，而是服务这个最终目标的“创作方法论学习引擎”：它从成功作品中重建可学习、可验证、可供用户参考的方法，而不只整理作品讲了什么。

用户一次导入整本小说，系统根据篇幅自动分层处理。人物、事件、时间线、事实、设定、伏笔、冲突和节奏是可核验的原料层；默认交付入口必须是按创作者问题组织的“创作学习报告”。用户不需要依次读完几十个数据库版块，也不需要在开书前自己回答全部问题；系统负责回答，用户负责判断答案是否有用、是否可信。

产品目标链固定为：

- 最终目标：AI 写作系统能够写出高质量百万字网文。
- 本系统职责：从成书中学习“开书前怎么决定、设定怎么准备、开篇怎么立住、连载怎么运转、长线怎么不崩、结尾怎么收束”。
- 默认用户出口：按创作问题和推荐阅读顺序组织的学习报告，而不是数据类型目录。
- 单书学习结算：形成有证据的创作学习报告，并区分可参考方法、不可复制条件和待跨书验证候选。
- 可信地基：每个关键答案可定位、可计数、带原文或明确结构证据；摘要只能导航，不能冒充方法论证据。
- 下游创作：用户与 AI 按创作步骤逐步完善自己的“最小开书包”；拆书结果只能由用户选择后作为参考，不能自动变成新书设定。共创不强制发生在本项目内，也不得以调用项目内 AI 接口为前提。
- 写作执行：用户确认的新书开书包还需按目标写作 Agent（智能体）的真实输入要求转换，形成目标专用交付物；写作 Agent 不直接消费某一本旧书的拆解结果，也不默认直接消费未经转换的通用开书包。

产品既不是一次性静态报告，也不是以资料归档为终点。主体是可持续核验、可修订的交互式方法论报告；证据资料库支撑报告，导出是附加能力。

### 2.2 产品北极星

对于任意篇幅的中文网文，拆书系统应回答一套沿真实写书步骤排列的创作问题，让用户看懂“作者可能做了什么选择、作品如何实现、能参考什么、哪些条件不可复制”。人物、事件、事实和证据重建是准确性地板；能说明“为什么可能有效、怎么做、能学什么、适用边界是什么”才是产品价值上限。

每项正式产出必须同时通过三问：

1. 它在回答哪一条带编号的北极星问题？
2. 结论能否定位、计数并回到原文或明确结构证据？
3. 它能帮助用户理解或判断什么？哪些部分可以参考、哪些不能直接照搬？

外部平台数据才能证明的因果不得伪造。本地拆书只能输出结构证据、风险候选和“待外部数据验证”。每本书必须记录平台与商业模式；付费与免费作品的跨书规律分开比较。

#### 2.2.2 42 问全量审计与共享能力包（2026-07-28）

42 问是产品验收主尺，不是 42 个串行开发任务。每问仍保留独立合同和状态，但建设顺序按共享原料合并为八个能力包；同一份经程序核验的账本可以支撑多问，不能为每道题重复拆书。跨包依赖只表示答案引用关系，不允许下游问题借上游“已就绪”绕过自己的证据检查。

状态词固定为：

- **完整答案可生成**：该问合同要求的实物、计数、证据和覆盖均通过程序检查。

- **原料未就绪**：现有数据只有摘要、少量案例或通用对象，尚不能支撑该问要求的全书覆盖、关系或计数。
- **条件未满足**：问题必须等待多书、平台元数据或用户选择；单书阶段只能给候选或保持未生成。
- **已回答**：正式答案已经持久化并通过证据引用校验；“专项账本完成”或“数据闸门通过”均不等于已回答。

| 8.5 | 口碑变化前有哪些可检测的结构异常信号？ |
| 8.6 | 对标书发布时题材处于红利期还是红海期，现在是否仍适用？ |

### 2.3 核心用户和价值

| 用户 | 主要需求 | 产品价值 |
|---|---|---|
| 当前核心用户：借助 AI 学习并创作网文的人 | 没有时间通读大量作品，也尚未形成卖点、设定、开篇、节奏、钩子、爽点和长线管理的方法 | 直接得到按创作顺序组织、可质检的学习答案，并按需收藏为新书共创参考 |
| 小说创作者、编辑和内容策划 | 复盘作品结构、验证写法、发现可复制方法和适用边界 | 比手工翻章更快得到有证据的方法论判断 |
| 后续通用用户 | 研究人物、事件、事实和跨章机制 | 可通过证据资料库追溯每项结论 |

首版不为只想得到几百字剧情简介、多用户协作、团队权限、商业计费或公开传播原文的场景设计。通用产品化后置，不能反过来稀释当前核心用户的创作学习目标。

### 2.4 核心用户任务

| 用户任务 | 系统应完成 | 结果 |
|---|---|---|
| 导入长篇小说 | 建立章节、原文位置和稳定来源索引 | 后续结果都能回查 |
| 学习一本作品 | 按北极星问题和推荐顺序组织答案，明确已回答、证据不足和未生成 | 用户先看到“这本书能教我什么”，不用在数据目录里找重点 |
| 结算单书学习 | 说明作者可能提前锁定的关键决策，区分可参考方法、不可复制条件和待跨书验证候选 | 拆完一本书有明确可带走的学习成果 |
| 收藏参考方法 | 由用户主动选择值得借鉴的方法卡，带入新书共创作为讨论材料 | 参考旧书原理，但不自动复制旧书设定和表达 |
| 共创新书开书包 | 在独立流程中由用户说明目标和判断效果，AI 主动提问、给方案并逐步记录确认结果 | 得到属于用户新书、可继续修订的最小开书包 |
| 交给写作 Agent | 只发布用户最终确认的新书开书包版本，并按写作环节裁剪所需上下文 | Agent 使用用户自己的创作决策，不直接使用旧书拆解 |
| 看到人物多个名字 | 归一身份并保留别名、置信度和争议 | 不拆散人物弧，也不误合并 |
| 追踪跨章事件和事实 | 建立事件时间线、事实版本和指定章节状态 | 能查询当时真实状态 |
| 阅读拆解结论 | 显示支持、反证、状态和来源 | 用户能判断可信度 |
| 修订或替换原文 | 标记受影响对象并局部重算 | 不让旧结果污染新版本 |
| 比较分析路线 | 显示质量、令牌、调用和时间 | 决定哪些机制值得保留 |

### 2.5 首版边界

- 中文小说优先，单用户，本机保存项目数据。
- 只设计、测试和验收 PC/桌面端浏览器，不做手机端。
- 支持短篇、中长篇、长篇和百万字以上作品，不设置统一小说字数硬上限。
- 第一批导入格式：TXT、Markdown、DOCX、EPUB。
- 首版使用用户配置的在线大语言模型，不要求用户运行本地模型。
- 质量优先，整本分析可持续数小时，但必须显示阶段、进度、失败原因和下一步。
- 第一版优先回答核心 42 问并形成可读、可核验的单书学习结算。主题和文风可后置；卖点、金手指、开篇、爽点、钩子、主支线、节奏、伏笔和长线管理属于核心方法论，不能整体推迟。复杂全局探索和正式报告导出后置。

### 2.6 明确不做

- 不做自动续写、仿写、整书改写或作者文风复制。
- 不做角色扮演聊天产品。
- 不因为参考项目存在“世界书”“角色卡”或“聊天记忆”就照搬同名功能。
- 不做多人协作、团队权限、云端账号和商业计费。
- 产品只记录 Token（令牌）、调用、重试、耗时、失败和缓存等运行数据；不提供模型单价、币种、金额、费用估算、费用汇总或价格快照。旧配置中的同类字段只为兼容读取而忽略，不能重新进入界面、接口或验收标准。
- 不把内部任务编号、租约代次、数据库编号和制品编号展示给普通用户。
- 不把自然语言摘要、社区报告、向量结果或流畅模型回答直接当作事实。
- 不让模型生成或选择任意数据库 ID，不让模型直接执行 SQL、代码或状态写入。

## 3. 产品原则

### 3.1 原文与证据优先

- 原文是最高权威来源。
- 每个正式人物、事件、事实和分析主张必须引用一个或多个原文证据。
- 摘要、图谱、社区报告、状态视图和自然语言解释都是派生结果，不能覆盖原文。
- 支持证据、反面证据、争议和未知必须显式保存。

### 3.2 结构先于报告

先产生可校验的人物、事件、事实、状态和分析主张，再编译自然语言说明。报告只能读取已经验证的对象，不能反向把编辑后的文字写成事实。

### 3.3 模型提议，程序决定

模型适合提出语义候选、判断相似性和生成解释；程序必须拥有：

- 稳定身份和来源位置。
- 数据结构和必填字段校验。
- 时间区间、权限和状态迁移。
- 合并、拆分、重定向和依赖传播。
- 数据库事务、文件提交和错误终态。

合法 JSON 只代表“可以解析”，不代表内容已经正确。所有模型结果都必须依次经过结构校验、原文对齐和领域规则。

### 3.4 不确定性不能被文字掩盖

候选可以进入有效、不确定或拒绝状态；事实可以争议或共存；主张可以部分支持、被反驳或证据不足。系统不能为了生成一份顺畅报告而强行二选一。

### 3.5 质量上限优先，但必须实测

首版先证明质量上限，不因未经测量的 Token 或耗时猜测提前删除可能有价值的机制；也不因为参考项目存在某机制就全部开启。高资源路线必须可开关、可观测，并通过金标、对照和消融实验决定默认开启、条件开启、人工触发、修复、延后或删除。

### 3.6 可恢复、可诊断、可重算

长流程必须可暂停、继续、重试和局部重算。失败时说明阶段、原因、影响和下一步。原文、身份、事件边界、事实或分析方案改变后，只重算依赖链受影响部分。

### 3.7 需求决定零件

参考项目是机制、思路和实现边界的来源，不是产品功能清单。研究和采用时必须区分：原项目功能、底层机制、我们的真实需求和最终产品功能。只有需求成立且机制合适时才吸收，并按许可证独立实现或登记复用。

### 3.8 证据等级纪律

- 源码已证实：可以追到固定版本的真实数据结构、调用链、写入、读取或持久化。
- 源码推断：根据代码结构作出的合理判断，必须说明尚未实际运行。
- 实际运行已验证：只有亲自执行并观察到行为时才能使用；仓库里存在测试文件不等于已经执行。
- 产品判断：根据本项目需求作出的采用、改造、延后或舍弃决定。
- 未知：缺少固定版本、真实服务、样本或运行证据，必须标明下一步验证。

README、论文、注释、营销文案和函数名只作为线索。函数存在不等于真实主链使用；提示词中的“必须”不等于程序硬规则；拥有 ID 字段不等于稳定身份；拥有时间字段不等于检索已经时点安全。

## 4. 项目、输入和来源规则

### 4.1 项目与版本

一个项目对应一部作品，可以包含多个明确的 `SourceVersion`（来源版本）。不同修订版、译本或章节切分不得静默混合。正文改变必须生成新版本，并建立旧版到新版的章节和证据映射。

### 4.2 导入流程

```text
创建小说项目
  ↓
选择 TXT / Markdown / DOCX / EPUB
  ↓
解析编码、标题、卷章和正文
  ↓
检查顺序、空章、重复章、异常短章、超长章和乱码
  ↓
用户查看章节树和正文抽样
  ├─ 有问题：修正标题、顺序、边界或重新导入
  └─ 无问题：确认来源版本
  ↓
建立稳定原文坐标和导入制品
```

### 4.3 导入问题和处理

| 问题 | 级别 | 处理 |
|---|---|---|
| 哈希相同的重复章节 | 阻塞 | 删除、只保留一个或明确标为重复版本 |
| 章节顺序冲突 | 阻塞 | 用户确认顺序 |
| 异常编码或替换字符 | 阻塞 | 重新选择编码或导入 |
| 空章、极短章 | 警告 | 可继续，但进入问题中心 |
| 超长章 | 警告 | 分块并保留完整章节来源 |
| 标题识别不确定 | 待确认 | 用户修正，不允许标题被当正文 |
| 自动场景边界不确定 | 待确认 | 场景仅为可重建派生边界 |

### 4.4 来源与证据坐标

- 字符偏移是原文定位主权威。
- 章节序号和段落序号用于结构与用户阅读。
- 令牌偏移是模型运行派生坐标，必须记录分词器版本。
- 跨段或跨章证据用 `EvidenceSet`（证据集合）组合，不创建虚假连续范围。
- 模型只返回引用文字时，定位器必须枚举全部精确匹配；零匹配拒绝，多匹配进入不确定状态，不能选择“最近一个”。
- 正式证据至少保存来源版本、章节、起止字符、文本快照和上下文哈希。
- 界面可以显示较宽上下文，但正式引用保持最小充分范围。

### 4.5 分块规则

分块是模型输入方式，不是原文结构。系统可以使用段落窗口、场景候选窗口、章节窗口和剧情阶段窗口；每种窗口保留重叠、来源和去重信息。跨块候选按来源坐标去重，不能因分块产生多个正式对象。

## 5. 用户流程和页面

### 5.1 首次拆解流程

```text
导入并确认整本小说
  ↓
人物识别与归一
  ├─ 查看人物、别名、证据和争议
  └─ 确认或标记问题
  ↓
剧情阶段与事件识别
  ├─ 查看跨章事件、参与者、时间和证据
  └─ 确认或标记问题
  ↓
事实、世界设定、人物状态和角色认知
  ↓
伏笔、冲突、节奏和场景功能
  ↓
进入统一工作台持续浏览、搜索、关联跳转和回查原文
```

每个阶段默认停在确认页。用户确认后才继续；标记问题时优先判断问题来自原文解析、程序规则、提示词、模型能力还是来源证据，不把人工修正当作掩盖系统问题的默认办法。

### 5.2 PC 端信息架构

| 页面 | 用户目标 | 主要内容 | 关键异常状态 |
|---|---|---|---|
| 项目首页 | 创建、进入和继续项目 | 项目列表、来源版本、最近进度 | 文件丢失、项目损坏、任务中断 |
| 创作学习路线 | 知道先看什么、看到哪里和下一问是什么 | 八阶段目录、每阶段进度、当前推荐问题、继续阅读 | 尚无答案、答案过期、专项原料未就绪 |
| 单问题阅读 | 一次判断一个答案有没有用、是否可信 | 一句话结论、关键指标、实现机制、可参考、不可照搬、限制、证据展开 | 部分回答、证据不足、反证或限制未处理 |
| 导入与章节确认 | 得到可信章节结构 | 文件导入、卷章树、正文预览、问题提示 | 编码错误、标题误识别、空章、重复章 |
| 阶段确认页 | 抽查并决定是否继续 | 总览、证据、问题标记、确认 | 结果为空、部分批次失败、证据失效 |
| 拆解工作台 | 浏览整本拆解结果 | 总览、人物、剧情、事件、时间线、事实状态、设定、伏笔、冲突、节奏 | 尚未生成、结果过期、上游修改 |
| 原文与证据 | 理解结论来源 | 章节树、正文、证据高亮、上下文 | 版本变化、位置失效 |
| 人物 | 追踪人物和关系 | 别名、身份、出现、关系、状态、人物弧 | 误合并、待拆分、身份争议 |
| 事件与时间线 | 追踪发生了什么 | 提及、正式事件、参与者、时间、因果和子事件 | 边界争议、共指不确定 |
| 事实与状态 | 查询某章成立的事实 | 事实版本、冲突、状态、角色认知 | 事实争议、时间不明 |
| 分析版块 | 浏览带证据的高层分析 | 剧情、伏笔、冲突、节奏、场景功能 | 证据不足、反证未处理 |
| 问题中心 | 集中处理问题 | 类型、影响对象、建议操作、重算范围 | 依赖冲突、修订影响下游 |
| 运行记录 | 了解长任务 | 阶段、批次、Token、调用、重试、耗时、失败、继续和停止 | 网络、限流、模型输出、恢复 |
| 设置中心 | 配置在线模型 | 模型服务、真实测试、分析方案、数据隐私 | 密钥、权限、参数、结构化输出失败 |

工作台第一入口是创作学习路线，内部按八阶段目录进入单问题阅读；证据资料库固定导航为总览、原文、人物、剧情、事件、时间线、事实与状态、世界设定、伏笔、冲突、节奏、问题。未完成模块显示“尚未分析”或“本版本尚未开放”，不能用模拟内容冒充结果。42 问不得渲染为 42 张同时展开的长卡片，用户通过“上一问/下一问”和阶段目录推进。

### 5.3 人工参与边界

普通高置信结果可抽样检查。用户重点处理：来源结构错误、人物误合并、事件边界争议、事实冲突、低置信分析和受修订影响的结果。合并、拆分和关键事实裁决必须可撤销并保留历史。

## 6. 输出体系

### 6.1 四层输出

| 输出层 | 内容 | 用途 |
|---|---|---|
| 创作学习层 | 按北极星问题组织的答案、推荐阅读顺序、未回答项、作者决策推断和可参考方法候选 | 默认入口和单书学习交付 |
| 机器权威层 | 来源、证据、正式人物、事件、事实版本、角色认知、已验证主张 | 查询、重算、审计和结构化导出 |
| 证据资料层 | 故事档案、原文、人物、关系、剧情阶段、事件、时间线、伏笔、冲突、节奏和世界规则 | 为学习答案提供浏览、核验和问题修订入口 |
| 运行审计层 | 问题、任务、版本、模型调用、令牌、重试、耗时、缓存和恢复 | 诊断、质量评测和资源优化 |

创作学习层内部再分三级：第一级是八阶段路线和当前推荐问题；第二级是单问题答案；第三级是按需展开的关键原文、反证和覆盖限制。人物六项账本、逐章章末钩账本等完整专项实物属于证据资料层，不得夹在学习答案之前或之间。默认页面顺序固定为“创作学习路线 → 单问题答案 → 按需证据 → 证据资料库 → 运行与问题”。数据数量和运行状态不能压过学习结论成为第一视觉重点。

### 6.2 证据资料库

| 版块 | 最低内容 |
|---|---|
| 全局剧情 | 章节范围、阶段目标、转折、未解决问题和证据 |
| 人物与关系 | 身份、别名、首次/最后出现、状态和关系变化、人物弧主张 |
| 事件时间线 | 原文提及、正式事件、时间、地点、参与者、时序、因果和子事件 |
| 事实与世界状态 | 世界规则、归属、能力、地点、阵营、有效区间和指定章节状态 |
| 伏笔与承诺 | 提出、强化、变形、部分兑现、兑现、失效和未回收 |
| 冲突与赌注 | 外部、内部、关系和规则冲突；升级、反转、解决和赌注变化 |
| 节奏与场景功能 | 铺垫、推进、揭示、反转、恢复、高潮和密度异常候选 |

钩子、爽点、压抑—释放、主支线配比和事件单元是核心创作问题，应逐步形成可计数曲线和有证据的候选；缺少专项分析时必须显示“未生成”或“尚不能回答”，不得以 `0` 冒充分析结论。名场面和情绪峰值属于候选分析，主题、母题和文风后置；主观判断必须标明适用范围和不确定性。

### 6.3 分析主张最低结构

每项重要分析至少包含：主张类型、结论、涉及对象、章节范围、支持证据、反面证据、验证状态、置信度、不确定原因和用户可读解释。

### 6.4 单书学习结算、新书共创与写作执行边界

每个拆书项目最终形成的是学习成果：

1. `创作学习报告`：按创作问题说明这本书怎么做、证据在哪里、用户能参考什么、哪些条件不能复制。
2. `可参考方法候选`：由用户主动收藏；区分单书候选、跨书已验证方法、个人风格和不可复制条件。单书结论只能标为 `N=1 待跨书验证`；进入已验证方法库至少需要同商业模式下多书证据，并保留反例与适用边界。

从成书倒推“作者开书前可能锁定了哪些决策”仍是有价值的学习问题，但输出名称必须是“作者决策推断”，不得叫作用户的“最小开书包”。

用户的新书最小开书包属于独立的共创项目：

1. 用户说明想写什么、想给读者什么体验及已有想法。
2. AI 按创作步骤主动提出问题、提供备选方案、解释影响，并记录用户确认与未确认项。
3. 用户可以引用自己收藏的拆书方法作为参考，但系统不得自动复制参考书的人物、世界、情节或表达。
4. 每一步形成一份或若干份用户可保存、复查和继续修改的结果；这些结果汇总成用户自己的开书包。
5. 开书包不是任何写作 Agent 的天然通用输入。选定目标 Agent 后，还要按其真实开书要求做转换；未经用户确认的共创结果和未经转换的通用内容都不得冒充目标 Agent 的权威输入。

新书共创已经形成 `/new-book` 首版内部载体和十步候选流程，但尚未经过用户真实新书共创，不能把当前步骤、字段和浏览器本地保存方式当成最终产品冻结。当前使用边界如下：

- 用户应先知道开一本书按什么顺序准备哪些内容，再逐步与 AI 交流并形成结果文件。
- 用户可以把项目给出的交流任务带到任意网页 AI 中完成，再保存、粘贴或导入结果；项目内置 AI 对话不能成为必经路径。
- “最小开书包”与更完整开书包的包含关系，Fable 原设计仍未完整定义；当前十步、五份文档和字段合同是沿 Fable 方法形成并已内部验证的首版候选，不得把用户的探索性举例或内部模拟结果冒充最终冻结规则。

写作 Agent 只能读取由用户确认内容转换而成的目标专用交付物。目标 Agent 需要哪些文件、字段和目录，必须检查其真实开书合同后再设计转换规则；不得先假定所有 Agent 共用一种输入。未经用户选择的拆书结果不得进入写作上下文。

### 6.5 导出

交互式方法论报告是主体。后续可提供 JSON 结构化包、CSV 指标、Markdown/HTML 报告和 DOCX；导出不得默认包含整部原文，只包含用户选择的引用和定位。

## 7. 总体系统形态

### 7.1 架构选择

首版采用本地优先的模块化单体：PC 浏览器界面、API 进程和本机 Worker（后台执行进程）共享同一领域模型、SQLite 权威数据库和文件制品目录。

```text
PC 浏览器界面
  ↕ HTTP + 进度流
应用 API
  ├─ 用户命令与参数校验
  ├─ 只读查询与页面投影
  └─ 任务登记
        ↕
本机 Worker
  ├─ 长时间模型调用
  ├─ 分批分析与局部重算
  └─ 制品提交与恢复
        ↕
SQLite + 不可变文件制品 + 可重建索引 + 在线模型服务
```

API 不在浏览器请求内同步运行整本分析；浏览器断开不能中断后台任务。首版不引入微服务、Redis、RabbitMQ、云数据库或图数据库。

### 7.2 组件职责

| 组件 | 负责 | 不负责 |
|---|---|---|
| PC 界面 | 项目、证据、问题、工作台和运行状态 | 直接修改数据库、决定稳定身份 |
| API | 参数校验、命令登记、查询投影和本地安全边界 | 同步执行长分析 |
| Worker | 领取任务、调用模型、提交制品、更新进度 | 绕过领域规则直接写权威对象 |
| 领域服务 | 身份、边界、事实、状态、检索、主张和依赖规则 | 依赖具体页面或模型供应商 |
| 模型网关 | 请求、超时、重试、限流、能力和用量 | 决定业务状态和权威写入 |
| 存储层 | 事务、版本、来源、索引和文件持久化 | 把派生摘要提升为事实 |

### 7.3 技术边界

- Python 后端，FastAPI 接口，Pydantic/JSON Schema 数据校验，SQLAlchemy/Alembic 数据库迁移。
- React + TypeScript + Vite 的 PC 端界面，只依赖 API 的用户投影，不保存领域权威。
- SQLite WAL 为首版权威事务库；全文检索、向量和图是可重建派生索引。
- 大型 JSON、报告和批次结果按内容哈希保存为文件，数据库登记身份、路径、状态和来源链。
- 在线模型和向量模型通过可替换接口接入，不绑定单一供应商。

### 7.4 Windows 启动与进程生命周期

- 最终用户只使用项目根目录的 `启动AI小说拆解工作台.bat`，不需要分别启动前端、API 和 Worker。
- 启动入口保留一个可见窗口，依次检查数据库、启动 API、启动 Worker、启动页面并自动打开浏览器；窗口显示当前状态、页面地址、日志位置和关闭方式。
- 页面固定使用 `http://127.0.0.1:15173`，API 固定使用 `http://127.0.0.1:18000`，避免与 SillyTavern 默认使用的 `8000` 端口冲突。
- 浏览器断开、刷新或关闭标签页不能中断数小时的分析任务；可见启动窗口才是本机系统的生命周期开关。
- 启动器只允许一个正式实例运行。API、Worker、前端及派生进程必须加入同一 Windows 作业组；正常关闭、按 `Ctrl+C`、启动失败或启动器进程意外消失时，作业组统一回收子进程。
- `dev.ps1` 和产品预览脚本只用于开发者调试，不能作为用户入口，也不能留下与正式数据库共用的旧 Worker。
- 每次运行使用独立日志目录；启动失败必须在窗口中说明失败步骤和日志位置，不允许安静失败。

## 8. 数据所有权和分层

### 8.1 权威顺序

```text
原始小说与来源版本
  ↓
章节、段落和原文证据
  ↓
人物 / 事件 / 事实候选
  ↓ 结构校验 + 原文对齐 + 领域规则
正式人物 / 事件提及 / 正式事件 / 事实版本
  ↓
人物状态、角色认知、关系图、剧情阶段和检索视图
  ↓
带支持与反证的分析主张
  ↓
伏笔、冲突、节奏等分析制品和工作台页面
```

上游修改必须标记受影响下游。来源、正式对象、派生视图、分析主张和自然语言报告分开保存。

### 8.2 对象所有权

| 对象域 | 核心对象 | 权威边界 |
|---|---|---|
| 来源 | Project、SourceVersion、Chapter、SourceUnit、EvidenceSpan | 原文与坐标最高权威 |
| 候选 | Entity/Event/Fact/Claim Candidate | 模型和规则提议，不能直接晋升 |
| 身份 | EntityMention、CanonicalEntity、EventMention、CanonicalEvent | 人物与事件稳定身份 |
| 事实 | Fact、FactVersion、FactEvidence、FactConflict | 事实命题、版本、区间和冲突 |
| 状态 | StatePatch、State-at-T | 从事实确定性重放的派生状态 |
| 认知 | ActorKnowledge | 某角色知道、相信、怀疑或隐瞒什么 |
| 检索 | TaskProfile、RetrievalCandidate、RetrievalRun | 任务材料选择和来源记录 |
| 主张 | AnalysisClaim、ClaimEvidence、ClaimJudgment | 已验证分析结论 |
| 叙事制品 | Promise、Decision、Arc、Report | 只消费验证结果的派生制品 |
| 运行 | Run、Task、TaskAttempt、Artifact、Blob、Issue、Metric、ModelCall | 任务、恢复、来源链和观测 |

### 8.3 单向晋升

```text
模型原始输出
→ 可解析候选
→ 数据结构校验
→ 原文位置校验
→ 领域规则校验
→ 有效 / 不确定 / 拒绝
→ 仅有效结果写入正式对象；不确定结果进入问题中心
```

禁止从“看起来合理”直接写正式对象。

## 9. 稳定身份、状态和审计字段

### 9.1 身份原则

- 来源内定位对象使用由版本和坐标计算的确定性身份。
- 跨版本人物、事件、事实和主张使用程序生成的持久身份。
- 自然语言名字、标题或模型返回 ID 不能作为主键。
- 合并不删除旧身份；旧身份重定向到保留对象并保留来源链。
- 拆分创建新身份，记录派生关系，不能静默复用旧身份表达多个对象。

### 9.2 身份类型

| 对象 | 身份依据 | 变化规则 |
|---|---|---|
| 来源版本 | 项目 + 标准化全文哈希 | 正文改变则新版本 |
| 章节 | 来源版本 + 顺序 + 标题/正文特征 | 新版本重建并映射 |
| 原文证据 | 来源版本 + 起止字符 + 文本哈希 | 文本或边界改变则新身份 |
| 人物/事件提及 | 原文证据 + 局部边界 | 原文或边界改变则新身份 |
| 正式人物/事件 | 程序生成持久身份 | 合并/拆分记录来源链 |
| 事实与事实版本 | 命题族身份 + 版本身份 | 追加版本，不覆盖历史 |
| 分析主张 | 程序生成身份 + 版本 | 修复产生新版本或派生主张 |
| 制品 | 类型 + 输入哈希 + 配置/代码/提示词版本 | 内容寻址且不可变 |

### 9.3 统一审计字段

正式对象至少记录项目、来源版本、状态、创建和更新时间、生成阶段、输入制品、证据、数据结构版本、代码版本、提示词版本、模型方案、置信度、不确定原因、替代对象和来源链。

### 9.4 核心状态

| 对象 | 状态 |
|---|---|
| 候选 | PROPOSED / VALID / UNCERTAIN / REJECTED |
| 正式人物/事件 | ACTIVE / MERGED / SPLIT / RETIRED |
| 事实版本 | ACTIVE / SUPERSEDED / INVALIDATED / DISPUTED / COEXISTING |
| 分析主张 | PROPOSED / SUPPORTED / PARTIAL / DISPUTED / CONTRADICTED / INSUFFICIENT / DROPPED |
| 制品 | WRITING / READY / FAILED / DIRTY / STALE / SUPERSEDED |

## 10. 人物身份归一

### 10.1 候选来源

人物候选可来自名称/别名、上下文语义、关系与角色、时间和共同出现约束以及用户词典。候选发现追求召回，正式合并优先保证精确率。

### 10.2 归一链

```text
人物提及候选
→ 名称、属性、关系和时间阻塞
→ 候选对及证据
→ 同一 / 不同 / 不确定
→ 聚类提议
→ 全聚类矛盾检查
→ 正式人物或待确认问题
```

### 10.3 硬性边界

- A 像 B、B 像 C 不代表 A 必然像 C，禁止无保护传递合并。
- 同场同时出现的独立角色、互斥属性和用户锁定“不同”是硬负例。
- 用户可锁定同一或不同，后续模型必须尊重。
- 合并、拆分和撤销会把相关事件、事实、状态、主张和报告标为过期并局部重算。

## 11. 事件发现、边界和跨章事件

### 11.1 三层身份

- `EventCandidate`：某条路线提出的候选。
- `EventMention`：原文中的一次具体提及，拥有稳定边界。
- `CanonicalEvent`：多个提及归并后的同一叙事事件。

三者不能混用。

### 11.2 候选路线

首版至少组合模型结构化提取和规则/状态变化两类路线；以后可增加触发词、事件类型查询、参数聚集和时间溢出路线。每条候选保留路线、模型、原始响应、文本、边界、参与者、时间、地点、置信度和证据。

### 11.3 原文对齐

| 输入 | 处理 |
|---|---|
| 字符位置和文字一致 | 接受对齐 |
| 只有令牌位置 | 用相同分词器投影到字符并记录版本 |
| 引用文字唯一匹配 | 补齐字符范围 |
| 多处精确匹配 | 保留全部位置候选并标记不确定 |
| 只有模糊改写 | 不直接落地，进入二次定位或人工确认 |
| 跨句描述 | 核心触发范围 + 多条支持证据，不制造虚假长范围 |

### 11.4 候选并集和边界裁决

多路线候选进入统一格式后，按同一窗口、范围重叠、包含、文本、类型、参与者和时间聚类。边界裁决选择最小充分触发范围；路线不一致或边界差异过大时进入不确定状态，不能取平均或选择最近同词。

### 11.5 正式事件和关系

正式事件归并综合事件类型、参与者、故事时间、地点、对象、叙事关系和文本语义。支持同一事件、前后/重叠、因果/条件、子事件以及报告、回忆、想象等叙事关系。想象、传闻和回忆不能自动当作当前真实发生。

## 12. 事实版本、状态和角色认知

### 12.1 事实与版本

`Fact` 表示稳定命题族，`FactVersion` 表示命题在某个有效区间的具体版本和证据。至少保存主语、谓词、对象/数值、观察章节、有效起止、可选故事时间、陈述方式、认知范围、置信度和状态。

### 12.2 更新规则

| 场景 | 表示 |
|---|---|
| 新事实替代旧事实 | 旧版本 SUPERSEDED，新版本从新章节生效 |
| 事实失效后再次成立 | 追加非连续版本，不覆盖旧区间 |
| 多个值同时成立 | 各自 COEXISTING |
| 来源互相矛盾 | DISPUTED，保留支持与反证 |
| 角色错误相信 | 写入角色认知，不写成读者事实 |
| 假设、计划、愿望 | 写入主张、承诺或角色认知，不当作已发生事实 |

禁止使用一个“当前值”覆盖历史，禁止把摘要中的事实直接写回事实库，禁止让模型选择任意数据库身份。

### 12.3 状态投影

事实库负责权威命题和版本；状态投影器按指定章节或故事时间，对经过校验的状态变更做确定性重放。状态快照是缓存，可从事实和变更重建，不是新的事实权威。

### 12.4 角色认知

角色认知与读者真相分开，至少支持：已知、相信、怀疑、未知、隐瞒和撤回旧信念。以角色视角查询时，在指定时间的客观状态上应用该角色可见性和信念，不泄露未来知识。

## 13. 任务相关检索和上下文选择

### 13.1 任务决定检索路线

不同任务不固定串行执行所有检索。`TaskProfile`（任务配置）决定范围、时间、人物、启用路线、每路配额、重排方式、是否必须反证、是否允许高资源全局路线以及模型方案。

### 13.2 路线

- 全文/词法：精确名字、原句、稀有词和规则。
- 向量：语义相似和改写。
- 人物/事件/事实：围绕正式对象扩展。
- 时间：指定章节、区间和前后变化。
- 局部图：参与者、物品、地点和相邻关系。
- 图扩散：从多个种子有界扩展。
- 社区/全局：全书结构和主题导航。
- DRIFT：复杂全局问题逐步下钻。

### 13.3 统一检索链

```text
任务意图
→ 路线激活
→ 各路线构造查询
→ 候选并集和统一格式
→ 分数归一/融合
→ 一次主重排
→ 路线配额和多样性
→ 回填原文来源
→ 最终上下文落点检查
```

不能把多个项目的融合、重排和图查询机械串联。全局摘要和社区报告只负责导航；最终上下文必须包含原文证据或可回源正式对象，并记录每条材料来自哪条路线。

### 13.4 条件触发，不做世界书

可吸收关键词、次级条件、优先级、预算和有界递归，用于选择相关人物、设定和历史证据。产品不创建世界书页面，不继承其字段、编辑器或聊天注入方式。

### 13.5 上下文预算

每次请求先预留任务约束、输出结构、当前原文、必须保持一致的正式对象和回复空间。剩余预算再按任务选择历史证据、世界设定、上游结构和示例。超出预算时记录省略内容和原因，不能静默截断原文。

故事结构和深层分析在长篇输入中先生成约 20～40 个连续章节范围导航；短篇则按实际章节数保留。每个范围记录起止章节、代表标题、代表事件、参与对象、事件与证据引用以及省略事件数量，用来证明全书哪些范围已经被看见。该导航明确标记为派生结果，只负责防止中间章节在全局请求中静默消失，不能代替正式事件或原文证据。分析方案已支持记录服务明确提供的模型上下文长度；有可靠数值时从上下文窗口扣除最大输出和安全预留，没有可靠数值时使用保守自动预算，并在运行诊断中记录预算来源。

模型标称上下文长度只定义“最多能提交多少”，不定义“在该任务上多少输入质量最好”。按用户 2026-07-28 的统一裁决，所有已配置模型和核心 42 问的**单次学习答案请求**先共用 15 万输入 Token（令牌）默认软上限，不再为每个“模型 × 问题”分别测试一套上限。该数值是运行天花板，不是必须填满的目标、最低材料量或模型质量保证：程序仍只装当前问题相关材料；模型可靠上下文不足时，先扣除最大输出和安全预留再自动收紧；超出时缩减无关材料或拆成连续窗口，每个窗口仍受单次上限约束。

这个统一软上限不抹平任务结构。人物事件抽取、4.9 逐章类型分类等局部任务可以基于证据粒度主动使用更小窗口；3.4 这种需要跨长篇寻找首次回应的任务可以使用多个不超过上限的连续窗口，并在全部实际钩子找到首次回应后提前停止，仍有未回应钩子时才扫到全书结尾。不得把多窗口总 Token 误写成单次输入，也不得因为上限是 15 万就添加无关材料。

基础人物、事件抽取的 `18,000` 当前单位是字符而不是 Token，只是局部窗口基线。它保留到同任务阶梯对照证明需要调整为止；跨批次连续性应通过相邻章节摘要、未完事件和状态衔接补足，不能用无上限放大单次原文窗口代替分层处理。

## 14. 分析主张、验证和专项分析

### 14.1 主张优先

专项分析器先输出最小可判定的结构化主张，不先写长文再反向猜证据。主张包含类型、对象、章节范围、命题、限定条件、所需证据类型、初始证据和版本。

### 14.2 验证链

```text
结构化主张
→ 检索支持证据
→ 检索反面或例外证据
→ 逐条判定
→ 冲突感知聚合
→ 支持 / 部分支持 / 争议 / 反驳 / 证据不足
→ 拆分 / 缩小范围 / 增加限定 / 补检索 / 删除
→ 已验证主张账本
```

逐条证据可标为支持、部分支持、反面、无关或模糊。禁止“只要一条证据支持，就把整条主张判为支持”；强支持与强反证同时存在时应进入争议或缩小主张成立范围。

### 14.3 六类核心分析器

| 分析器 | 主要输入 | 输出 |
|---|---|---|
| 剧情结构 | 事件、事实、章节功能、全局检索 | 阶段、转折、目标、障碍和剧情弧 |
| 人物与关系 | 人物、指定章节状态、角色认知、事件 | 人物弧、动机和关系变化 |
| 伏笔与承诺 | 事件、主张、词法和时间检索 | 提出、强化、变形、兑现和失效 |
| 冲突与赌注 | 事件、目标、关系和世界规则 | 类型、升级、反转、解决和赌注变化 |
| 节奏与场景 | 章节/场景指标、事件、对话和动作 | 场景功能、密度、转场和节奏异常 |
| 世界规则 | 事实版本、例外和状态 | 规则、限制、代价、例外和违反 |

### 14.4 报告编译和反馈隔离

报告只消费正式对象和已验证主张，自动插入来源，检查矛盾和缺失引用。用户修改报告文字时，应转化为修订主张、处理问题或增加人工注释，不能把报告文本写回事实库。

## 15. 后台任务可靠性

P0 可靠性已经实现并通过自动测试和 Windows 强制中断恢复验证。以下契约继续约束所有后续长任务。

### 15.1 不变量

1. 一个任务最多只有一个当前有效尝试。
2. 领取任务是数据库原子事件；未领取成功的 Worker 不得调用模型。
3. 尝试次数只在成功领取时增加。
4. 每次领取生成新的尝试身份、租约代次和不可复用令牌。
5. 心跳、成功、失败、制品预留和发布都验证完整租约身份。
6. 旧 Worker 的迟到响应不能修改任务或制品终态。
7. 达到最大次数的任务必须失败或取消，不能永久运行。
8. 成功、失败和取消是普通执行路径不能反向离开的终态。
9. 同一任务的一种最终结果只有一个制品身份，内容去重不能破坏来源链。
10. 数据库和文件系统的中间状态必须可扫描、判断和恢复。
11. 模型调用期间不持有数据库写事务。
12. 时间、令牌、退避和故障点可注入，测试不依赖真实长时间等待。

### 15.2 任务和尝试状态

```text
PENDING → RUNNING → SUCCEEDED
                  → RETRY_WAIT → RUNNING
                  → FAILED
                  → CANCEL_REQUESTED → CANCELLED
PENDING / RETRY_WAIT → CANCELLED
```

尝试状态包括运行、成功、可重试失败、永久失败、租约过期、取消和旧尝试。`max_attempts=3` 表示最多真实执行三次，包括第一次。

### 15.3 原子领取和租约隔离

SQLite 使用短事务和条件更新领取任务；领取事务内禁止模型、文件和网络操作。Worker 领取后关闭会话，使用独立心跳续租。所有提交携带任务、尝试、令牌、代次和 Worker 身份；不匹配返回租约丢失、旧尝试、已请求取消或任务已终止。

### 15.4 重试和取消

过期扫描器处理租约过期：已请求取消则取消；次数耗尽则失败；否则进入等待重试。超时、限流和临时不可用可以重试；认证、错误参数和不支持任务永久失败。取消等待任务立即生效；取消运行任务进入“正在取消”，随后提交被租约条件拒绝。重复取消幂等。

### 15.5 Provider（模型服务）失败约定

模型服务通过注册表注入，不由任务内部直接创建。稳定错误至少包括：超时、限流、临时不可用、非法输出、认证失败、错误请求和不支持任务。错误对象必须携带稳定错误码、是否可重试和建议等待时间。

### 15.6 多服务失败确认与恢复

分析方案可以保存一个主服务以及有顺序的备用服务和对应模型。任务创建时固化完整服务路线，运行中修改设置不会让旧任务暗中改用其他模型。超时、限流、服务不可用和无法安全修复的模型输出在同一服务连续失败 3 次后暂停；密钥失效、服务未配置和请求被明确拒绝时首次失败即暂停，避免重复发送必然失败的请求。

暂停后不得后台自动切换。工作台必须同时显示当前服务、当前模型、失败原因，以及已配置时的下一备用服务和模型，并让用户选择“切换备用服务继续”“继续使用当前服务重试”或“停止本次分析”。主服务稳定可用即可开始并完成日常分析，不要求用户为了使用产品主动测试备用服务；备用服务只是主服务故障时的可选保险，未配置或未测试都不能阻塞正常分析。重试当前服务会从新的连续失败区间重新计数；切换后沿用同一任务、来源、输入、尝试历史和制品身份继续，不能另建重复人物或事件；所有服务都失败或没有下一个备用服务时终止本次任务并保留上一版有效工作台。每次切换决定进入任务诊断，服务链只向后推进，不允许无限循环。

## 16. 制品、崩溃恢复和局部重算

### 16.1 制品和 Blob 分离

`Artifact`（制品）表示某个任务结果及来源链；`Blob`（内容文件）按哈希存放不可变内容。不同任务内容相同可以共用 Blob，但必须拥有各自的 Artifact。

### 16.2 提交流程

```text
模型返回并通过校验
→ 写尝试专属临时文件并计算哈希
→ 在租约条件下预留 WRITING 制品
→ 原子提升为内容寻址 Blob
→ 再次验证租约、代次和哈希
→ 同一数据库事务完成：制品 READY + 任务成功 + 尝试成功
```

临时文件、WRITING 记录、孤儿 Blob、缺失文件和哈希不匹配都必须能由恢复器扫描。重复恢复安全；旧尝试结果标为 STALE，不能覆盖当前结果。

### 16.3 依赖和 DIRTY（过期）传播

| 上游变化 | 直接受影响 | 后续传播 |
|---|---|---|
| 原文/证据 | 人物、事件和事实候选 | 正式对象、索引、主张、报告 |
| 人物合并/拆分 | 事件、事实和角色认知 | 状态、关系图、分析和报告 |
| 事件边界/归并 | 事件、事实和伏笔 | 时间线、剧情/冲突分析、报告 |
| 事实版本 | 状态和世界/人物主张 | 报告和导出 |
| 提示词/模型/方案 | 该阶段制品 | 只传播到依赖该制品的下游 |
| 报告模板 | 报告 | 不重算人物、事件、事实和主张 |

源文本修改产生新来源版本，通过哈希和映射找到受影响证据，沿依赖图标记过期并重算最小子图。旧制品保留版本和差异，不能直接覆盖。

## 17. 在线模型、分析方案和提示词

### 17.1 设置中心只有两层

- 模型服务：名称、类型、接口地址、访问密钥、连接状态和模型目录。
- 分析方案：某类任务使用哪个服务、模型、参数、提示词和失败策略。

一个服务可以供多个任务使用；人物抽取、事件分析、事实核对和全书归纳不应共用一套固定参数。

### 17.2 连接成功的层级

界面必须区分配置已保存、地址和密钥可访问、模型目录读取成功、所选模型有权限、所选模型支持当前任务的结构化输出和参数。“读取到 20 个模型”不能显示成“已经可以拆书”。

### 17.3 参数原则

- 没有任务实验依据时使用“自动”，不发送温度、采样或推理字段。
- 模型或服务不支持的参数不显示、不发送。
- 输出长度按连续整数设置，不使用无依据的 256 步长。
- SillyTavern 的聊天默认温度 1.0 和项目旧值 0.2 都不能直接成为小说任务默认值。
- 所有非本机模型地址统一使用流式传输：包括当前和未来新增的中转站、官方远程服务、主服务和备用服务。只有 `localhost`、`127.0.0.0/8` 和 `::1` 回环地址可以继续使用整包返回。远程服务即使接受 `stream=true`，若实际不返回流式数据，也必须在模型测试和正式调用中明确报错，不能静默退回整包模式。
- 流式片段在本机完整拼接后，继续经过既有 JSON 解析、结构校验和证据校验；服务返回的输入与输出 Token 继续记入调用诊断，服务未返回时明确记为未知，不估算也不换算金额。连接方式不改变分析方案原有的超时和重试设置。
- 每次运行记录实际服务、模型、参数、Token、调用、重试、耗时和方案版本。

### 17.4 能力记录

服务能力至少记录模型目录、普通请求、严格结构化输出、普通 JSON、推理强度、最大输出字段、流式响应、上下文和输出上限。能力来自已知规则、小内容真实测试和用户手工覆盖，不能只按模型名猜。

当前真实长篇使用本机 `geminicli` 服务和 `gemini-3.1-pro-preview` 模型，回环地址采用整包返回，单次超时 360 秒。Google 官方模型页确认该模型输入上限为 1,048,576 Token、输出上限为 65,536 Token（`https://ai.google.dev/gemini-api/docs/models/gemini-3.1-pro-preview`）；当前分析方案据此保存 1,048,576 的可靠上下文长度。此结论只适用于该模型；其他没有可靠服务说明或实测证据的模型继续使用保守自动预算，不能按名称类推。

### 17.5 提示词编排

提示词不是一个巨型文本框，而是按任务保存目标、原文、正式对象、约束、输出结构、示例和失败降级等组件。每个组件有标识、版本、顺序、适用任务和令牌数。运行记录保存最终实际请求的脱敏版本、原始响应、解析结果和修复尝试。

组件按稳定性排序：系统指令、输出结构、原文窗口等稳定组件前置，任务特定内容与易变字段（时间戳、任务编号等）置后，禁止在请求前缀插入每次都变化的内容。该纪律以保持前缀可被服务商提示缓存复用为依据，但不承诺任何缓存收益指标；收益随消融实验按 19.7 实测记录。

### 17.6 密钥和配置恢复

密钥与普通设置分开保存；前端默认只知道是否设置，不回传完整值。密钥不进入项目导出、日志和 Git。模型服务和分析方案保存前保留配置快照；项目数据、模型设置和密钥分别备份，恢复前说明覆盖范围。

### 17.7 长调用反馈

点击开始后立即显示当前阶段、批次、整体进度和预计剩余时间。停止后先显示“正在停止”，后台在安全边界取消。用户离开页面任务继续，返回后恢复真实状态。完成、部分完成、停止和失败必须有不同说明和下一步。

## 18. API、隐私和安全

### 18.1 命令与查询分离

创建项目、导入、开始分析、解决问题、合并人物和重算属于命令；项目、证据、人物时间线、状态、主张和运行指标属于只读查询。界面不能提交任意状态、数据库身份或审计字段。

### 18.2 本地与隐私

- 默认只监听 localhost。
- 小说、项目数据、数据库、制品、日志和密钥不提交 Git。
- 模型服务方案明确是否允许发送原文、最大窗口和脱敏要求。
- 日志不打印完整章节，只记录哈希、证据身份和必要短片段。
- 导出不默认包含整部原文。
- 删除项目和清理模型原始响应需要明确确认和审计。

### 18.3 安全边界

- 小说正文作为数据块，与系统指令和输出结构隔离，降低提示词注入风险。
- 所有文件路径由工作区服务解析，禁止路径穿越。
- 模型输出不能作为 SQL、Python 或模板代码执行。
- 密钥通过本机安全存储，不由普通 API 回传。
- 制品使用哈希、原子写入、结构校验和恢复对账。

## 19. 质量、金标和验收标准

### 19.1 测试语料

使用约 5 万字、50 万字和 100 万字以上样本验证。语料应包含别名、假身份、同名人物、关系变化、跨章事件、回忆/转述、事实失效和重新成立、角色误解、伏笔与普通描写并存以及章节修订。

### 19.2 金标原则

被评测的同一模型不能自动生成并直接确认答案。AI 可以提出候选，但高风险金标需人工确认并保留争议说明。至少 20% 高风险样本进行第二轮复核。

建议金标覆盖人物提及、正式人物、事件提及、正式事件、事实版本、指定章节状态、分析主张和伏笔生命周期；数量随样本规模调整，不再绑定旧 30～50 章固定数量。

最小金标前移：首次统一真实体验验收（22.5.2）的同一时间窗内，建立 5 万字档最小金标子集与对拍脚本。样本必须覆盖别名、同名、跨章事件、事实失效等 19.1 要求的现象；允许用系统输出预标注、人工确认并做 20% 二轮复核；首批标注人物提及、正式人物、正式事件，并预先标注 20～30 条核心事实。对拍脚本自动计算人物归一精确率/召回率与事件发现召回率，读数纳入 19.7 观测记录。读数本身不新设阻断阈值；显著低于 19.4 目标时先立问题单、按 19.6 结果处理规则分析原因再决定开发顺序。事实正确率的首个真实读数是 P3 质量评测的第一里程碑，对照 19.4 的 ≥0.90 目标按 19.6 处置。

### 19.3 硬性闸门

- 正式对象的证据回贴率 100%。
- 正式对象数据结构校验通过率 100%。
- 孤儿引用为 0。
- 同输入重复运行不产生重复正式对象。
- 模型超时、非法输出、进程中断和局部重算均可恢复。
- 证据错位、跨项目污染、无效身份和不可恢复的 P0 错误为 0。

### 19.4 初始质量目标

这些是首轮实验目标，不是宣传承诺；调整必须记录样本、原因和影响。

| 对象 | 初始目标 |
|---|---:|
| 人物归一精确率 | ≥ 0.95 |
| 人物归一召回率 | ≥ 0.85 |
| 事件提及发现召回率 | ≥ 0.80 |
| 事件边界宽松 F1 | ≥ 0.85 |
| 事件边界精确 F1 | ≥ 0.70 |
| 跨章正式事件归并 F1 | ≥ 0.80 |
| 事实正确率 | ≥ 0.90 |
| 事实有效区间准确率 | ≥ 0.85 |
| 指定章节状态准确率 | ≥ 0.90 |
| 主张证据充分率 | ≥ 0.90 |
| 最终核心主张无充分证据比例 | ≤ 0.05 |

专项分析人评关注事实正确、证据充分、结构洞察、不确定性和可用性。核心事实错误率不高于 5%，重要主张证据覆盖 100%。

### 19.5 错误等级

| 级别 | 示例 | 处理 |
|---|---|---|
| P0 阻断 | 证据指错、身份冲突、跨项目污染、无法恢复 | 必须修复，不能验收 |
| P1 严重 | 人物误合并、关键事件漏失/误归并、错误事实写入 | 修复并重跑受影响评测 |
| P2 重要 | 主张证据不足、伏笔过度解读、时间因果错误 | 进入问题中心，不能发布 |
| P3 一般 | 措辞、排序和次要可读性 | 后续迭代 |

### 19.6 对照和消融

至少比较普通章节摘要+全局总结、只有原文检索+结构化主张、完整质量模式。优先测试关闭多路线事件、反面证据、人物归一、图/社区、指定时点状态和二次主张修复后的质量、Token 与耗时变化。

在上述对照臂之外新增一条正式对照臂 A（2026 长上下文强基线）：以现有管线为底座，单强模型 + 大窗口（5～10 万令牌含重叠）+ 严格结构化输出 + 逐条原文引用 + 程序精确匹配回验。其中“长上下文全局身份提议”仅作为人物归一的候选提议路线接入 10.3 既有校验链，模型不得直接拥有合并决定。5～10 万令牌只属于该消融对照臂，不得成为正式学习答案或其他任务的默认预算。该臂用于检验多路线机制相对 2026 年长上下文模型能力的真实增益，处置沿用本节六档规则；反证检索、硬负例保护和不确定性显式保存属于产品定义（2.1/3.1/3.4/6.3/10.3/14.2），不进入“须胜出对照臂才保留”的赌局，只接受实现方式层面的消融优化。

轻方案基线臂（普通章节摘要+全局总结）允许在 P6 之前提前运行：按 19.7 完整记录 Token、调用、重试、耗时和失败，产出报告可即刻交付创作参考并归档为 P6 对照的固定基线材料。评审采用双轨标准——创作场景可用性与抽样回贴核查（随机抽 20 条结论人工回贴原文）并列记录，不以任一轨单独定胜负；提前运行只产出数据，不触发任何“重管线收缩”决策，收缩须待可公平对照后按 1.3 以 ADR 另行决定。

尚未实现的高资源路线（图扩散、社区/全局、DRIFT）在既有后置基础上增加立项门槛：只有当对照臂 A 或完整质量模式在其对应任务类型（全局结构问答、多跳关系查询等）上出现已测得的质量缺口时才启动实现——用测得的缺口立项，不用未测的猜测立项或废案。

结果处理：质量显著则保留；只对特定任务有效则条件开启；质量增益小但昂贵则人工触发或延后；可通过缓存/批处理改善则修复后复测；连续两轮仍不稳定或引入严重错误则删除。

### 19.7 观测字段

每次模型调用和阶段运行记录：运行/阶段/任务/来源和制品版本、服务/模型/提示词/参数、输入输出和缓存 Token、字符和对象数、开始结束和耗时、重试/超时/错误码、金标子集、问题数和接受/修复/拒绝数量。开始前按当前分批、全局分析次数和最大输出计算调用次数与 Token 保守上限，运行后采用服务实际返回的 Token；服务未返回时明确标为未知，不能用金额或自造数据代替。批处理 API 只作为可能的吞吐优化路线，不进入产品计费能力，也不改变第 15 章已验证的任务模型；是否启用必须由真实吞吐、稳定性和维护复杂度验证。

归一化指标包括每 1 万字的 Token、调用、重试、耗时和失败率；每章、事件、事实和已验证主张的 Token；缓存命中、局部重算节省，以及各路线相对新增 Token 与耗时带来的质量增益。

### 22.5.8 Fable 决策优先级与补缺方法校正（2026-07-27）

- **用户纠正**：用户对“最小开书包是否属于完整开书包”等表述是在探索自己的理解，不等于已经批准产品结构。除用户明确否定的内容外，Fable 已作出的明确决定优先；Fable 没有设计完整的部分，才由后续 AI 沿其方法论补充。
- **Fable 的既定方法**：用户提供的是可能不全、也可能不对的原材料；AI 应从网文作者、写书步骤、AI 写作管线和读者市场等专业视角主动补全，按写书时间轴综合，保留“用户原话 / 合理引申 / 专业补充”来源，做保真核查后给用户一份可直接挑毛病的候选实物。
- **本次撤回的过早结论**：此前提出的“基础必选 / 条件必选 / 可选增强 / 后续任务”四层清单和固定四区页面，没有 Fable 明确证据，也未获用户确认，当前降级为未采纳候选，不得进入实现。
- **当前证据判断**：Fable 明确了“最小开书包”的倒推目标、必备项/建议深度/使用证据、按写书阶段使用和锁死层/生长层边界；没有明确设计“完整开书包包含最小开书包”的产品层级，也没有定义跨网页 AI 的共创载体。前者待专业重组，后者按用户当前使用要求补充。
- **结果标准化目标**：用户希望共创过程可以多轮，但正式结果文件应保持少量、稳定和可复用；人物等对象需要统一字段，并区分真正必需、按条件启用和无剧情用途时不填的内容，同时说明需要写到什么深度。该体验目标已确认，具体文档数量和字段表仍属于候选设计，必须按 Fable 的方法给出实例后再冻结。

- **字段模型**：必要程度（必填/条件必填/选填）、锁定时机（开写前锁定/暂定/可延后）和确认状态（已确认/暂定/刻意留白/不适用）分别记录，不再混成单一优先级。
- **实例结果**：用一部虚构都市异能样本完整填写五份文档，总计约 8,300 个字符，单份约 1,200～2,300 个字符；固定检查确认只有五份正式文档、无占位词和整段重复，核心机制、人物、世界、第一卷与连载账本在跨文件关键词上保持一致。
- **语义修正**：实例发现原暂定书名承诺“刀”，正文核心却是“借十分钟能力”，已修正书名并把“书名承诺是否与卖点、能力和开篇一致”补为正式检查字段。这证明字段完整检查不能替代跨文档语义审查。
- **北极星覆盖复核**：初版约 6,000 字符只覆盖第一至第五节相关问题约一半，能证明格式但不能证明内容够用。补入第五份动态账本后覆盖明显提高，但世界长线梯度、平台参数和跨书证据仍不完整；预计完整简单样本会自然落在约 12,000～18,000 字符，仅作为当前覆盖差额的工程估算，不是硬字数门槛。
- **验证边界**：当前只验证一个男频都市异能样本，不能据此冻结五份文档或全部字段；仍需真实用户新书共创和不同题材样本。写作 Agent 转换尚未设计完成。

### 22.5.10 跨网页 AI 的阶段式引导共创（2026-07-27）

- **页面流程已基本确认**：新书共创按步骤推进；每一步先说明要做什么、为什么现在做，允许用户输入明确想法、模糊倾向或“完全没有灵感”。页面把阶段协议、已有相关内容和用户原话合成可复制提示词，用户可带到任意网页 AI 讨论。
- **AI 行为合同**：网页 AI 必须先复述并确认理解，再每轮最多追问三个高价值问题；用户没想好且需要 AI 设计时，至少提供三个核心机制或实际影响不同的方案，说明优势、风险以及对后续人物、世界和剧情的影响，不能用换名字冒充三个方案。
- **实时问题**：用户询问“目前什么题材火”等当前市场问题时，有联网能力的网页 AI 必须搜索、注明时间和来源；没有联网能力时必须暴露限制，不得把旧知识伪装成当前结论。
- **阶段结束合同**：AI 根据本阶段完成标准判断并明确输出“已形成结果 / 无正式结果 / 尚未结束”之一；形成结果前必须获得用户确认。无结果结束必须说明原因、最迟重开时机和对后续步骤的影响。
- **回到项目后的确认**：用户默认只粘贴固定的阶段结束块，不需要搬运完整聊天记录；页面检查阶段编号、必填字段、依赖和冲突，预览将写入或修改的内容，只有用户确认后才更新正式开书包并进入下一步。
- **第 0～9 步内部流程已收口（2026-07-27）**：`/new-book` 已形成一套配置驱动的十步流程，每一步都支持“自然语言起点 → 复制便携提示词 → 粘贴固定阶段结束块 → 三态识别与标准字段校验 → 预览写回与依赖影响 → 用户确认”。步骤依次覆盖灵感与约束、品类承诺、核心发动机、主角、人物班子、最内圈世界、第一卷、开篇施工、一致性检查和连载运行合同；已确认内容只按相关文件注入下一步。页面累计维护并下载 `00_开书总表.md`、`01_人物与关系.md`、`02_世界与规则.md`、`03_剧情与开篇.md` 和 `04_连载规则与账本.md`，同一标准字段只保留最新确认版本，不按对话次数增加正式文件。前序步骤重新确认后，后续结果和受影响文档保留但全部标记为需要复核；复核完成后可恢复十步齐备状态。页面仍不调用项目内 AI、不把拆书结果自动写入新书设定、不保存完整网页聊天；浏览器本地保存仍不是按多本新书管理的最终持久化方式。

## 23. 用户验收边界

用户只验收产品功能和使用效果，不验收分支、PR、数据库迁移、任务租约、制品编号和自动测试。

内部样板、单步页面、自动检查和模拟交互先由 AI 自行完成，不作为要求用户参与的阶段验收门。用户不需要在主体拆书器尚未形成整体真实使用流程时提前试用新书共创；等整体项目达到可完成真实任务的状态后，再安排一次有意义的端到端实测。

正式验收节点：

1. 能导入真实整本小说、正确显示章节，并得到真实人物和事件结果。
2. 人物、剧情、事件、事实、伏笔、冲突等核心版块完整可浏览，并能回查原文。
3. 整本长篇从导入连续运行到完整工作台。

## 27. 最终执行规则

1. 产品开发只以本文件为总入口，并在任何规划前执行第 0 章的优先级、证据和数据准入检查。
2. 声称“Fable 已决定”时必须能回查第 0.3 节原始证据；无证据的内容只能标为后续候选。
3. 用户纠偏发生后，必须清理基线、代码、测试、提示词、界面和计划中的同类错误，不得只在进度记录末尾补一句说明。
4. 需要具体机制的源码证据时，按第 20.2 节回查对应 P01～P19 档案。
5. 需要工程操作时，使用仍在维护的 `engineering/`、ADR、迁移、测试和脚本。
6. 不再创建并列的产品总览、路线图、实现审计、研究总评或旧阶段总方案。
7. 如果本文件缺少后续开发所需的重要产品或系统信息，应直接补充本文件，而不是恢复旧文档让读者拼接。
