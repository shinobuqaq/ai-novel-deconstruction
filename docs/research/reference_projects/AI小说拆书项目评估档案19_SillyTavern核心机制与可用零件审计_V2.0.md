## 1. 这次为什么重写 P19

P19 V1.0 详细研究了模型连接、模型目录、参数预设、连接配置和服务能力差异。这些结论仍然有效，但它只回答了“设置中心可以向 SillyTavern 学什么”，没有回答“SillyTavern 本体还有哪些机制能为小说拆解工作台提供零件”。因此，V1.0 不能被当作 SillyTavern 的完整可用机制审计。

V2.0 在保留 V1.0 有效细节的基础上，补查以下与当前产品明确相关的部分：

1. 提示词的分层、顺序、触发、导入和导出。
2. 上下文令牌预算、强制预留和超额处理。
3. 条件触发、递归扩展、优先级和预算内选择。
4. 向量分块、重叠、阈值、多集合查询和进度反馈。
5. 密钥保存、遮蔽、多密钥和暴露边界。
6. 参数预设、连接配置、配置备份和恢复。
7. 最终请求、令牌构成和前后请求差异诊断。
8. 扩展清单、依赖、版本和加载失败边界。
9. 流式进度、停止、最小化和后台继续的交互机制。
10. SillyTavern 本体实际提供和没有统一提供的重试边界。

V2.0 不是用摘要覆盖旧文，而是完整吸收 V1.0 仍有效的模型连接、参数、能力适配、落地约束和源码回查信息，再扩大研究范围、纠正无依据结论并建立面向本产品的零件取舍矩阵。迁移审计完成后，V1.0 的 Markdown 和 Word 已失去独立职责并删除；后续只使用本文件，不需要回翻旧版补充细节。

## 2. 审计边界

本档案不是“SillyTavern 所有代码和所有扩展的百科全书”，也不声称已经穷尽未来所有可能用途。那种范围无法被可靠验证，而且会重新落入“先研究功能，再硬找用途”的问题。

本次采用需求驱动边界：只审计当前统一产品基线已经提出的需求，以及未来 P1～P5 明确需要的支撑机制。以后产品出现新的真实需求时，再对固定版本或新版本做定向补查，并记录为 P19 增补，而不是重新凭印象设计。

每项判断固定区分四层：

1. 原项目功能：SillyTavern 实际提供什么。
2. 底层机制：撇开聊天产品外形后，真正可复用的办法是什么。
3. 我们的需求：小说拆解工作台是否确实需要它。
4. 最终去向：直接吸收、改造吸收、只学思想、明确舍弃或必须自研。

例如，SillyTavern 的“世界书”是原项目功能；关键词与次级条件、扫描深度、递归触发、优先级和令牌预算是底层机制；我们的需求是为某次人物、事件或设定分析选择相关证据；最终功能是“任务相关证据选择”，不是“世界书”。

## 3. 证据等级与许可证边界

- 已验证：直接读取固定提交的源码、界面定义、默认值、请求构造和后端保存逻辑。
- 代码推断：根据前后端调用链判断用户操作结果，但没有连接所有付费服务逐个实测。
- 产品判断：结合小说拆解工作台的需求，决定吸收、改造、舍弃或自研。
- 未验证：不同中转服务对兼容接口、结构化输出和特殊参数的真实支持程度；需要用真实服务测试。

SillyTavern 使用 AGPL-3.0。当前项目默认只吸收机制并独立实现，不复制源码和界面代码。任何直接代码复用必须先完成许可证评估、第三方代码登记和发布义务确认。

## 4. 总体结论

SillyTavern 对我们的价值不只是 API 设置。它提供了九类值得吸收的成熟机制：

1. 服务、模型、参数预设和连接配置分层。
2. 根据服务能力显示并发送参数。
3. 提示词组件化、顺序化、按任务触发并可导入导出。
4. 先预留必要内容，再在剩余上下文预算内装配材料。
5. 按条件、优先级和预算选择相关信息。
6. 检索分块、阈值、Top-K、多集合查询和可见进度。
7. 密钥与普通设置分离，前端默认只知道是否已设置。
8. 记录最终请求和各部分令牌占比，支持前后差异诊断。
9. 长调用可见进度、停止、最小化和后台继续。

但它不是我们的基础框架，也不是小说拆解引擎。它的权威对象是聊天、角色和消息；我们的权威对象是小说版本、章节、原文证据、人物、事件、事实、状态和分析主张。任务恢复、证据坐标、跨章归一、事实版本、崩溃恢复和阶段确认仍必须按本项目设计实现。

## 5. 模型连接、目录与真实测试

### 5.1 四层结构

SillyTavern 把模型调用拆成不同层次：

1. 模型服务连接：服务商、接口地址、访问密钥和连接状态。
2. 模型目录：从服务读取可用模型，同时允许手工填写未返回的模型。
3. 参数预设：温度、最大回复长度和采样参数等可以保存和切换。
4. 连接配置：把服务、地址、密钥、模型和参数预设组合成可复用配置。

自定义兼容服务同时提供模型下拉列表和手工模型名称。模型目录不可用或目标模型未返回时，用户仍能手工填写，不会被 `/models` 接口卡死。

固定回查位置：

- 服务、密钥和模型控件：`public/index.html:2898-4060`
- 模型列表整理与回填：`public/scripts/openai.js:2001` 附近
- 连接状态检查与真实测试：`public/scripts/openai.js:4374`、`:5910`、`:6045`
- 连接配置字段、创建、应用和更新：`public/scripts/extensions/connection-manager/index.js:38-431`

### 5.2 “读取到模型”不等于“可以分析”

模型目录解决的是方便选择，不是证明模型可用。必须区分：

1. 配置已保存。
2. 地址和密钥能访问。
3. 模型目录读取成功。
4. 所选模型有调用权限。
5. 所选模型支持当前任务需要的输出格式和参数。

因此，“读取到 20 个模型”只能证明模型目录接口基本可用。我们的设置中心必须增加“测试所选模型”：发送极短、低 Token 请求，分别验证普通生成、结构化输出、关键参数和错误翻译。

### 5.3 对本项目设置中心的落地约束

模型服务至少包含：服务名称、服务类型、接口地址、访问密钥、连接状态、最近测试时间、读取模型和测试所选模型。用户可见状态必须区分：尚未保存、已保存但未测试、地址与密钥可访问、模型目录读取成功、所选模型测试成功，以及带具体原因的测试失败。

分析方案至少包含：方案名称与用途、模型服务、模型、最大输出长度、温度或自动、服务支持时的推理强度、超时和自动重试。人物事件抽取、章节总结、人物归一、时间线核对、伏笔分析和全书归纳可以使用不同方案。质量或资源档位只能在样本实验后建立，不能用未经验证的一组固定参数冒充正式档位。

高级参数只有在当前服务支持、范围有依据、用户能看懂、保存后真实生效且失败时能指出具体字段的情况下才展示；模型目录不可用时必须保留手工模型名称，不让发现接口成为使用阻断点。

### 6.2 对 256 步长的正式结论

拆书项目此前把最大输出长度写成 `step=256`，浏览器因此拒绝 30000，并建议 29952 或 30208。后端只要求整数范围，SillyTavern 同类字段也使用 `step=1`。因此，256 是没有产品、接口或模型依据的前端错误，已经修正。

以后每个参数的最小值、最大值、步长和默认值必须注明来源：服务官方限制、模型元数据、任务质量实验或明确的产品保护规则。

### 6.3 对默认温度 0.2 的纠正

SillyTavern 固定版本默认温度是 1.0，但这只能证明“它的聊天默认值是 1.0”，不能直接证明“小说结构化抽取也应该固定为 1.0”。同样，拆书项目此前使用 0.2 也没有产品文档或实验依据。

正式规则是：

- 服务支持省略温度时，任务方案默认使用“自动”，即不发送该字段。
- 服务要求温度时，先用服务默认值或模型明确推荐值。
- 人物事件抽取、文学分析、章节总结等任务分别通过样本实验确定，不设置一个全局固定温度。
- 界面显示“自动”或具体数值，并记录实际发送值，不能让默认值暗中生效。

### 6.4 能力适配比参数数量重要

“OpenAI 兼容”只代表接口大体相似，不代表每个参数、结构化输出、推理字段和模型目录完全相同。SillyTavern 为 OpenAI、OpenRouter、Azure OpenAI、Ollama、vLLM 等维护不同参数集合。

我们的服务能力记录至少应包含：

| 能力 | 状态形式 |
|---|---|
| 模型目录 | 支持 / 不支持 / 未测试 |
| 普通请求 | 成功 / 失败 / 未测试 |
| 结构化输出 | 严格 JSON Schema / 普通 JSON / 不支持 / 未测试 |
| 推理强度 | 支持的值 / 不支持 / 未测试 |
| 最大输出字段 | `max_tokens` / `max_output_tokens` / 其他 |
| 流式响应 | 支持 / 不支持 / 未测试 |
| 上下文与输出上限 | 已知数值 / 服务未提供 |

能力由“已知服务规则 + 真实低 Token 测试 + 用户手工覆盖”共同确定，不能只根据模型名字猜。

请求构造不得向所有兼容服务统一强发推理字段或严格 JSON Schema；读取模型目录成功也不得冒充真实调用成功。失败原因至少区分地址、密钥、模型权限、参数不支持、结构化输出不支持、超时和限流。

## 7. 提示词编排不是一个大文本框

### 7.1 原项目机制

`PromptManager`（提示词管理器）把提示词作为有标识、可启停、可排序、可按生成类型触发的组件管理。`getPromptCollection` 按既定顺序收集已启用且符合触发条件的组件；提示词和顺序可以导出为带版本的数据，也可以导入并验证结构。

固定回查位置：

- 管理器和配置：`public/scripts/PromptManager.js:300-360`
- 按顺序和触发条件收集：`public/scripts/PromptManager.js:1510-1553`
- 导出、校验和导入：`public/scripts/PromptManager.js:1786-1867`

### 7.2 可转化的零件

我们的分析任务也不应由一个难以追踪的大提示词字符串组成。建议按任务保存以下组件：

1. 任务目标与输出对象定义。
2. 原文片段和稳定来源坐标。
3. 已确认的人物、别名、事件或事实上下文。
4. 本轮必须遵守的约束。
5. 输出结构和字段说明。
6. 正反例或边界案例。
7. 失败时允许的降级说明。

每个组件记录标识、版本、顺序、适用任务、是否启用、来源和令牌数。运行记录保存最终实际请求，而不是只保存模板名称。

### 7.3 不照搬

不照搬角色扮演主提示、越狱提示、角色专属拖动顺序和聊天注入名称。普通用户也不需要直接拖动所有提示词组件。首版由系统维护任务级编排；开发诊断页允许查看最终请求和组件占比。

结论：改造吸收，代码独立实现。

## 8. 上下文预算与必要内容预留

### 8.1 原项目机制

SillyTavern 的 `ChatCompletion`（聊天请求装配器）先用上下文上限减去回复预留，得到可用输入预算。它支持检查某条或一组消息是否放得下、为必要内容预留预算、插入消息、移除消息并归还预算。

固定回查位置：

- 初始化和设置预算：`public/scripts/openai.js:3817-3894`
- 插入、删除和预算增减：`public/scripts/openai.js:3896-3980`
- `canAfford` 与 `canAffordAll`：`public/scripts/openai.js:3982-3999`
- `reserveBudget` 等预算操作：`public/scripts/openai.js:4098-4145`

### 8.2 对小说拆解的转化

每次模型调用都应有明确预算，而不是“能塞多少塞多少”。建议先预留：

1. 输出结构和任务约束。
2. 当前需要分析的原文正文。
3. 必须保持一致的正式人物、事件或事实标识。
4. 结构化输出所需的回复空间。

剩余预算再按任务选择历史证据、相关人物、世界设定、上游摘要和辅助例子。超出预算时必须记录哪些材料被删减、为什么删减，不能静默截断原文。

SillyTavern 的“从聊天历史末尾删除较旧消息”不能直接用于小说。小说证据选择必须考虑章节位置、事件关联、人物相关性、事实有效期和原文来源。

结论：预算机制直接吸收思想；小说材料排序与删减策略必须自研。

## 9. 条件触发机制，不做世界书

### 9.1 原项目机制

`world-info.js` 提供主关键词、次级关键词、逻辑条件、扫描深度、递归触发、最小激活、优先级、分组评分和令牌预算。它在有限上下文中选择当前对话相关条目，并允许已选条目的内容进一步触发其他条目。

固定回查位置：

- 全局扫描和预算设置：`public/scripts/world-info.js:65-82`
- 主次关键词与选择逻辑：`public/scripts/world-info.js:130-470`
- 设置加载与边界：`public/scripts/world-info.js:797-983`
- 主扫描和激活流程：`public/scripts/world-info.js:4597` 附近

### 9.2 对小说拆解的转化

可用机制是：

- 条件触发：当前章节出现人物、地点、组织、物件或规则时，选择相关正式对象和证据。
- 次级条件：只有同时满足人物和地点、物件和状态等条件时才引入材料。
- 预算内选择：按任务相关性、证据等级、时间有效性和优先级装配。
- 有界递归：相关对象可以继续带出直接依赖，但必须有最大层数和预算。
- 来源记录：每条被选材料都记录触发原因和原文来源。

我们的产品不创建“世界书”页面，不继承世界书字段、编辑器、聊天扫描深度和注入位置。最终落地是任务相关证据选择、世界设定回查和人物状态查询。

结论：只吸收机制，产品形态明确舍弃。

### 10.2 对小说拆解的取舍

适合参考：分块与重叠的可配置方式、阈值和 Top-K（返回数量）分离、多集合查询、去重、进度和失败反馈。

## 11. 密钥、连接配置与预设生命周期

### 11.1 密钥管理

SillyTavern 把密钥与普通设置分开保存。前端通过密钥状态知道某项是否已配置，默认不能读取完整值；后端只有在明确开启 `allowKeysExposure` 时才允许查看，多种服务使用独立键，并支持同一服务保存带标签的多个密钥记录。

固定回查位置：

- 密钥类型和前端映射：`public/scripts/secrets.js:19-220`
- 密钥管理器、写入和读取：`src/endpoints/secrets.js:1-580`
- 完整值暴露开关：`src/endpoints/secrets.js:540-580`、`:642-643`

我们的设置中心应继续坚持：

- 普通设置接口不返回完整密钥。
- 界面只显示已设置、未设置和必要的尾部遮蔽信息。
- 密钥不写入项目导出、日志、Git 或错误详情。
- 服务删除、密钥删除和分析方案解绑必须分开处理。
- 多账号确有使用需求时再增加带标签密钥，不为了功能数量提前暴露复杂度。

结论：安全边界直接吸收，存储实现独立完成。

### 11.2 参数预设

`preset-manager.js` 覆盖保存、更新、另存、重命名、删除、导入、导出和恢复默认等完整生命周期。它的价值不是聊天预设本身，而是让一组参数成为有名称、可比较、可恢复的正式对象。

对我们的转化：分析方案应支持复制、重命名、停用、导入、导出和恢复系统默认；修改时明确影响哪些后续任务，不暗中改写已完成运行的历史参数。

固定回查位置：`public/scripts/preset-manager.js`。

### 11.3 连接配置

连接管理器把 API 类型、地址、模型、参数预设和密钥选择组合成连接配置，并按顺序恢复。对我们来说，这不是另建一个用户难懂的“连接配置”产品，而是分析方案内部引用一个模型服务和一个模型。

用户看到的仍然只有两层：模型服务和分析方案。内部可以借鉴组合与恢复机制。

固定回查位置：`public/scripts/extensions/connection-manager/index.js:38-431`。

## 12. 配置备份与恢复

SillyTavern 会在启动和自动保存流程中为设置创建备份，抑制内容完全相同的重复备份，列出快照并允许载入或恢复。

固定回查位置：

- 自动备份和重复抑制：`src/endpoints/settings.js:35-201`
- 快照列表、读取、创建和恢复：`src/endpoints/settings.js:298-369`
- 启动备份：`src/endpoints/settings.js:377-381`

我们的设置中心和小说项目都需要更清楚的恢复边界：

- 模型服务和分析方案保存前保留旧版本。
- 用户可以恢复最近一次可用配置。
- 项目数据、分析结果和密钥分别备份，避免一个快照把三类数据混在一起。
- 恢复前说明将覆盖什么，不恢复已删除密钥的完整值。

结论：配置快照机制改造吸收；小说项目级备份另行设计。

## 13. 最终请求与令牌诊断

`itemized-prompts.js` 会保存请求材料，计算角色描述、世界信息、历史消息、提示词等部分的令牌数和占比，显示使用的模型、接口、预设和分词器，还能查看原始最终请求并比较前后两次请求差异。

固定回查位置：

- 保存和读取分项请求：`public/scripts/itemized-prompts.js:15-106`
- 分项令牌和运行信息：`public/scripts/itemized-prompts.js:109-225`
- 原始请求与差异：`public/scripts/itemized-prompts.js:248-329`

对小说拆解的直接价值很高。每次分析运行至少应记录：

- 任务类型、提示词版本、服务、模型和实际参数。
- 输入原文章节和来源版本。
- 每类材料的令牌数、选择原因和被裁剪内容。
- 最终发送请求的脱敏版本。
- 原始响应、解析结果、修复尝试和稳定错误码。
- Token、耗时、重试次数和最终状态。

普通用户页面只显示通俗摘要，例如“本轮使用 8 个章节片段，因上下文上限省略 3 条低相关证据”；完整请求只在内部诊断入口查看，并必须隐藏密钥和敏感请求头。

结论：诊断思想直接吸收，用户界面改造，数据结构独立实现。

## 14. 扩展边界和模块化

SillyTavern 的扩展系统包含清单、依赖、最低版本、禁用状态、发现、加载错误和生命周期钩子。它说明成熟系统需要让可选能力明确声明依赖和失败原因，而不是把所有功能硬塞进核心流程。

固定回查位置：`public/scripts/extensions.js` 及后端扩展端点。

当前项目不需要建设通用插件市场。我们的优先级是完成 P1～P5，继续保持模块化单体：导入器、模型服务、提示词编排、人物、事件、事实状态、检索和分析模块拥有清楚接口；可选模块加载失败不能拖垮整本项目。

结论：只学模块边界和能力声明；插件平台明确延后。

## 15. 长任务进度、停止与后台继续

`streaming-display.js` 提供运行中状态、模型图标、推理和正文流式更新、停止按钮、最小化、关闭但后台继续、停止状态和完成状态。

固定回查位置：

- 状态和停止回调：`public/scripts/streaming-display.js:28-132`
- 最小化与后台继续：`public/scripts/streaming-display.js:135-219`
- 停止和完成状态：`public/scripts/streaming-display.js:291` 以后

我们的任务通常持续数分钟到数小时，不能照搬聊天气泡式浮层，但可以吸收交互原则：

- 点击开始后立即反馈，不让用户怀疑按钮无效。
- 明确显示当前阶段、当前批次、整体进度和预计剩余时间。
- 停止操作立即进入“正在停止”，后台在安全边界取消。
- 用户离开页面后任务继续，返回后恢复真实状态。
- 完成、部分完成、已停止和失败使用不同状态和下一步。

我们已有比 SillyTavern 更强的后台租约、恢复和制品幂等机制，因此只吸收用户反馈方式，不照搬它的聊天生成生命周期。

结论：交互改造吸收，可靠任务核心保留自研实现。

## 16. 重试能力的证据边界

本次没有确认 SillyTavern 本体对所有模型请求提供统一、稳定、带最大次数和错误分类的自动重试层。部分请求或扩展可能有自己的重试处理，但不能据此写成“SillyTavern 已提供统一重试机制”。P01 研究的插件能力也不能归到 SillyTavern 本体。

因此，本项目继续使用自己的 Provider Failure Contract（模型服务失败约定）：超时、限流、认证失败、非法输出、永久失败使用稳定错误码，明确哪些可重试、何时重试和最大次数。SillyTavern 只作为错误反馈和连接测试的参考，不作为任务可靠性来源。

结论：统一重试必须自研。

## 18. 对当前项目设计的具体更新

P19 V2.0 应进入统一基线，但不是把全部研究正文复制到总文档。统一基线只保存当前决策和索引，详细证据继续保存在本档案。

需要同步的产品设计：

1. 设置中心继续使用“模型服务 + 分析方案”两层。

3. 增加所选模型真实测试和服务能力记录。
4. 提示词按任务组件化、版本化，保存最终请求。
5. 每次调用先预留必需材料和回复空间，再按预算选择证据。

7. 运行记录增加材料构成、令牌、裁剪和请求诊断。

## 21. 最终决策

P19 V2.0 作为 SillyTavern 与本项目当前需求相关的正式机制审计档案。它保留 V1.0 的模型连接和参数细节，并新增提示词、预算、触发、检索、安全、快照、诊断、模块边界和长任务反馈。

最终原则：先由我们的产品需求决定要找什么零件，再从 SillyTavern 等参考项目中吸收成熟机制；吸收机制不等于复制原功能，更不等于复制源码。没有证据支持的参数使用“自动”或标为实验设置；没有完成真实模型调用的连接状态不能显示成“可以拆书”；任何重要分析都必须保存最终请求、模型版本、实际参数和原文证据来源。
