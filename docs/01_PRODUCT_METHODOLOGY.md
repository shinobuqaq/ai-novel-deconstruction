# 01 产品哲学与创作方法论白皮书

> **文档性质**：AI 小说拆解工作台产品定位、设计哲学、权威决策规则与创作方法论的唯一核心依据。  
> **面向读者**：产品设计者、核心开发者、创作者及后续协作 AI。

---

## 0. 永久记忆锚点与权威层级

在长周期开发与上下文迭代中，任何新会话或新参与者接手时，必须严格遵守以下决策程序与权威层级，三者绝非平行的折中意见：

```text
+-------------------------------------------------------------+
| 1. 用户（最高决策权与最终裁决权）                            |
|    - 确定业务大方向、使用方式、系统边界与最终验收标准        |
|    - 口语指令与纠偏覆盖一切旧表述与旧实现                   |
+-------------------------------------------------------------+
                              ↓ (指导与约束)
+-------------------------------------------------------------+
| 2. Fable（总设计路线）                                      |
|    - 不违背用户决定的前提下，负责具体方法论、问题框架与产出设计 |
|    - 默认约束，不得因个人偏好或实现方便静默替换              |
+-------------------------------------------------------------+
                              ↓ (执行与填补)
+-------------------------------------------------------------+
| 3. 执行者 / 协作 AI                                          |
|    - 忠实落地代码与测试，在 Fable 真实留白处沿其思想补充     |
|    - 代码与测试是实现证据，不得反向覆盖产品哲学与有效路线    |
+-------------------------------------------------------------+
```

### 权威执行细则：
1. **用户拥有最高裁决权**：用户明确纠正的目标、边界和使用方式，自动覆盖 Fable 和其他 AI 的历史表述，也覆盖建立在旧前提上的现有代码。
2. **Fable 的已定详细路线必须继承**：在未与用户决定冲突的部分，Fable 核实的方法论框架、产出格式、证据标准和执行顺序是默认约束。
3. **真实留白处方可补充**：补充必须标明“后续推导”，不得将个人猜测伪称为已定规范。
4. **代码与测试是载体，不是更高权威**：当发现代码或测试与既定产品路线冲突时，修正代码或文档，不得拿现状反推改变产品初衷。

## 1. 系统本质与唯一定位

### 1.1 创作方法论学习引擎（Learning Engine for Novel Crafting）
- **核心定位**：本系统的唯一职责是作为**服务小说创作者的“方法论研习引擎”**。
- **原料不是终点**：从整本小说中抽取的人物、事件、事实、伏笔、冲突等，只是底层的“事实原料”。系统的核心价值在于**将原料提炼升华为网文创作方法论洞见**。
- **不直接充当写作 Agent 的前置输入管道**：
  - 系统的产出是给**人类创作者阅读、思考、套用模板**的，不是为了生成一堆格式化的 JSON 直接灌给某个自动写书机器人。
  - 用户读完拆解研报后，带着明确的框架去构思自己的新书。
- **绝不伪造外部数据因果**：
  - 单本小说的拆解只能提供**文本客观事实、作者决策推断与参考候选**；
  - 严禁在缺乏真实全网数据的情况下，伪造“因为主角在第3章装逼，所以本书当月追订上涨50%”这类虚假的外部市场因果。

## 2. 核心创作哲学与判定铁律

### 2.1 原料准确是第一关，方法论洞见是价值上限
1. **原料必须可核实、可定位**：
   - 每一个人物出场、每一个剧情事件、每一个伏笔铺设，必须能够精确定位到章节、字符偏移量并提取原文证据切片。
   - 杜绝“大模型信口开河的大段概括”，一切推论基于客观存在的文本证据。
2. **模型提议，程序决定**：
   - 大语言模型（LLM）负责提出观察提议、分析候选与文学解释；
   - 程序逻辑负责硬性校验：实体一致性、章节范围、时间线先后顺序、数量统计与引文真实性。

### 2.2 客观事实硬校验 vs 主观文学判断软包容（用户纠偏铁律）
系统必须将所有规则严格区分为两栏，坚决防止“程序过度越权代替创作者进行审美判断”：

| 校验类别 | 程序处理方式 | 涵盖范围 |
| :--- | :--- | :--- |
| **客观事实校验** | **程序硬失败（Hard Failure）** | 章节/事件归属、字符位置、时间先后顺序、数量与覆盖率、是否有原文证据支持、是否存在未被证明的外部因果。 |
| **主观文学判断** | **软性包容（Soft Framework）** | 欲望是否“足够深”、动机或底线是否完美符合特定范式、钩子强度偏好、文学风格分析。这些由模型提出解释并呈现证据，**由人类创作者保留最终审美与裁决权**。 |

> **重要禁忌**：严禁使用“必须同时满足固定文学条件清单”作为拆解成立门槛。只要存在有证据支持的局部变化、性格加深或反差，程序就必须允许保留，不得因未凑齐“动机—选择—结果”完整链条而将整条分析抹杀。

## 3. 创作者交互与呈现原则

1. **认知减负与分层交付**：
   - 42 个北极星问题是系统的底层分析合同，绝不能当成“用户的调查问卷”。
   - 创作者界面只呈现清晰有序的研报结论；底层的庞大证据账本、长文本引文默认收敛，提供按需查看机制。
2. **渐进式沉浸阅读**：
   - 遵循写书的自然认知旅程：**先看开篇怎么抓人（黄金三章与核心卖点） → 再看人物如何立住（主角与配角班底） → 再看连载节律（爽点密度与章末钩） → 最后看长篇纵深（伏笔与世界观）**。
3. **层级 3：实操工具包交付标准**：
   - 每一个创作问题的最终研报，必须达到“工具包”级别：
     - ① 为什么这个问题对写书至关重要；
     - ② 从拆解数据中提取的真实标杆案例；
     - ③ 可迁移的通用写作方法论；
     - ④ 包含自检清单、常见错误避坑、可直接套用的填空模板与参考数值。

## 4. 历史教训与防走偏防线（十条避坑警钟）

回顾系统演进过程中出现的偏差，后续任何迭代必须严格警惕以下 10 大教训：

1. **切勿混淆工程通路与原料就绪**：接口能调通、页面能展示、测试能通过，绝不等于专项拆书原料已经合格。
2. **切勿用整屏大杂烩铺满页面**：避免将人物、伏笔、章末钩、几万字原料全平铺在一个滚动页上，必须分层收纳。
3. **切勿盲目把大模型当全知权威**：模型只能提出候选，必须由程序校验客观事实、人类做主观决策。
4. **切勿制造整体门槛阻塞局部产出**：单题原料具备即可生成该题答案，不得因为无关问题未就绪而阻止已有问题交付。
5. **切勿把所有材料塞进单次超长请求**：必须按问题相关性设置单次分析 Token 上限（建议 15 万 Token 软上限），避免注意力涣散与超时失败。
6. **切勿在长输出场景沿用本机整包响应**：长文本生成任务必须支持流式传输或阶段落盘，避免网络或超时中断导致计算结果全部丢失。
7. **切勿过度设计不可维护的中间过渡态**：拒绝“投影”与“程序编译”双轨硬编码，统一由高内聚的插件声明自身行为。
8. **切勿靠手工 dict 操作与正则处理模型返回**：模型返回值一律采用现代 Pydantic V2 严格结构化模型解析，不合格当场重试或纠偏。
9. **切勿让技术调试信息干扰创作主屏**：底层 Prompt、Raw JSON、Token 计费与单模块排查必须独立在诊断面板中，主屏只留纯粹创作空间。
10. **切勿在缺乏样本时强行推断题材差异**：在未拆解第二本不同题材网文前，各实操工具包中的“题材差异”一律标注“待补充”，不强行臆造。
